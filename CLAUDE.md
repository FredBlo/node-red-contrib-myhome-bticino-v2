# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Node-RED node pack (`node-red-contrib-myhome-bticino-v2`) that lets Node-RED flows control BTicino/Legrand MyHome™ home-automation devices (lights, shutters, scenarios/CEN, thermostats, energy meters) over the proprietary SCS bus, via a gateway that speaks the OpenWebNet (OWN) protocol over TCP.

There is no build step, bundler, or test suite — this is plain CommonJS Node-RED node code, installed and run directly by Node-RED.

## Commands

There are no npm `scripts` defined (no build/test/start commands). Development commands available:

- `npx eslint .` — lint JS and HTML files (config in [eslint.config.js](eslint.config.js))
- `npx prettier --check .` / `npx prettier --write .` — check/apply formatting (config in [.prettierrc.js](.prettierrc.js))
- `npm publish` is done via CI ([.github/workflows/npm-publish.yml](.github/workflows/npm-publish.yml)), triggered on GitHub release publish — not run manually.

To manually exercise a node during development, install this package into a local Node-RED instance's `~/.node-red` (or link it) and import one of the flows in [examples/](examples/) via the Node-RED editor's Import dialog.

## Architecture

### One config node + one connection node + N device nodes

- **`myhome-gateway`** ([myhome-gateway.js](myhome-gateway.js)) is the Node-RED *config* node. It owns the single TCP `net.Socket` to the physical/virtual gateway (host/port/password), performs the OpenWebNet login handshake (open password or HMAC SHA-1/SHA-2), and auto-reconnects with backoff on error/close. Once connected, it parses incoming OWN frames, buckets them by "WHO" family (lighting=1, automation/shutters=2, temperature=4, CEN=15/CEN+=25, energy=18, other), and re-emits them as Node.js EventEmitter events (`OWN_LIGHTS`, `OWN_SHUTTERS`, `OWN_TEMPERATURE`, `OWN_SCENARIO`, `OWN_ENERGY`, `OWN_OTHERS`) that other nodes subscribe to via `RED.nodes.getNode(config.gateway)`.
- **Device nodes** (`myhome-light`, `myhome-shutter`, `myhome-scenario`, `myhome-thermo-central`, `myhome-thermo-zone`, `myhome-energy`) each reference a `myhome-gateway` config node and:
  1. Listen for the relevant `OWN_*` event and parse/track state in an in-memory `payloadInfo` object, emitting flow messages on change (with "SmartFilter" logic to suppress redundant output).
  2. Handle `input` messages from the flow (topic `cmd/<topic>` to send a command, `state/<topic>` for a read-only status refresh) by building an OpenWebNet command string and sending it through the gateway via `mhutils.executeCommand`.
  3. Register/deregister their event listeners via `mhutils.eventsMonitor`, and clean up on the node's `close` event.
- **`myhome-eventsession`** / **`myhome-commandsession`** are lower-level nodes: `eventsession` opens a raw monitoring session on the gateway to surface all matching bus frames as-is (used for discovery/monitoring flows); `commandsession` sends a raw OpenWebNet command string and returns the response(s), used by the "MH Inject" example flows.

### Shared logic: [myhome-utils.js](myhome-utils.js)

All nodes require this module rather than duplicating protocol logic:
- `processInitialConnection` — drives the connect/login state machine (`disconnected` → `handshake` → `authenticating[_HMAC[_HashSent]]` → `connected`), shared by both `myhome-gateway` (monitoring session) and `myhome-commandsession` (command session).
- `executeCommand` — opens a short-lived command-session TCP connection, sends one or more OWN commands in sequence (with optional inter-command delay), and collects ACK/NACK + responses per command.
- `eventsMonitor` — small class wrapping `EventEmitter` add/removeListener bookkeeping so device nodes can cleanly unsubscribe from the gateway's `OWN_*` events on node `close`.
- `buildSecondaryOutput` — builds each device node's second output message (boolean / text-state / arbitrary dotted-path property extraction) from the node's `payloadInfo`.
- `calcPass` / `calcHMAC` — implement BTicino's basic and HMAC (SHA-1/SHA-2) password hashing schemes for gateway authentication.
- `logNodeEvent` — routes debug/log/warn/error output through the calling node's own logger (`node.debug/log/warn/error`) at a configurable severity.

### Node pairing convention

Every runtime node `myhome-X.js` has a matching `myhome-X.html` (Node-RED editor UI: config form + help text, registered via `RED.nodes.registerType` in client-side JS) and is declared in the `node-red.nodes` map in [package.json](package.json). Both the `.js` and `.html` need updating together when a node's config fields change.

### Internationalization

Each node's HTML/JSON strings are localized under [locales/](locales/) — `en-US` (default), `fr`, `nl` — mirroring the root file names (e.g. `locales/fr/myhome-light.json`). When adding or changing user-facing strings in a `myhome-X.html`/`myhome-X.js`, update the corresponding keys in all three locale sets, not just `en-US`.

**The `"common"` block and `_version_common`**: every node's own locale file (`locales/<lang>/myhome-<node>.json`, all 9 node types × 3 languages = 27 files) starts with an identical `"common": {...}` block - shared strings like `"name"`, `"topic"`, the riser/local-bus dropdown options, SmartFilter/skip-events/read-only checkbox labels, secondary-output config strings. This is a deliberate, unavoidable duplication, not an oversight: Node-RED's i18n has no cross-node-shared namespace - both the editor's `scope._('key')` and a runtime node's injected `RED._('key')` **auto-prefix the key with that specific node's own module namespace** unless the key already contains a `:` (confirmed straight from Node-RED's own source - editor-side in `@node-red/editor-client`'s bundled `red.js`, `definition["_"] = function() {... args[0] = definition.module+":"+args[0] ...}`; server-side identically in `@node-red/registry/lib/util.js`'s `createNodeApi`, `red["_"] = function() {... args[0] = node.namespace+":"+args[0] ...}`). There is no way for one node's locale file to serve as a shared source that another node's `._()` calls can resolve against - each node can only ever look up keys inside its own namespace, so a string genuinely shared across node types has to be copy-pasted into every node's own file.

The `"common"` block's first key, `"_version_common": "YYYY.MM.DD"`, exists **purely to catch a missed propagation** - it is not read by any code. It is deliberately kept **byte-identical across all 27 files** (confirmed: as of this writing every file has the exact same value). Whenever you add, remove, or edit any key inside a `"common"` block:
1. Make the exact same change to the `"common"` block in **every other** `locales/<lang>/myhome-<node>.json` file (all 3 languages × all 9 node types), not just the file you started in.
2. Bump `_version_common` to today's date, in **every one of those 27 files**, so they keep matching each other.
3. Before finishing, spot-check with `grep -rh "_version_common" locales/ | sort -u` - it should print exactly **one** unique line. More than one means the propagation was missed somewhere.

### CHANGELOG.md style

Entries describe **end-user visible impact**, not the internal/technical reason for a change. For a bug fix, say what was broken from the user's perspective and what now works (e.g. "the X checkbox had no effect; it now correctly enables/disables Y") — leave out implementation detail like exact variable/key names, the specific line that was wrong, or why the bug happened. That kind of technical detail belongs in code comments or in this file, not in the changelog.

### BUS addressing

Device addresses use MyHome's `A/PL` (address/point-light) scheme encoded as a single string (`A=1,PL=5` → `"15"`; 4-digit form when A or PL > 9). Zone/light groups are prefixed with `#`, and non-default bus levels append `#4#<level>`. This encoding/decoding logic lives inline in each device node (see `node.lightgroupid` construction in [myhome-light.js](myhome-light.js) for the canonical pattern).

### Gateway BUS points registry (v3.0.0+, Light + Shutter + Energy + ThermoZone share the multi-category UI)

`myhome-gateway` carries a `points` array (config property) letting users maintain a friendly registry of known AP. Each entry is `{category, room, description, icon, pointid, isgroup, ...}`; `category` (`'light'`/`'shutter'`/`'energy'`/`'thermozone'`) lets one array serve every category, each as its own collapsible section, sharing an `editableList`-based UI (row = summary + expandable detail, same pattern as `myhome-scenario`'s `rules`). Started editor-only, but `myhome-gateway.js` now also copies it onto the runtime node (`node.points = config.points`) so device nodes' server-side `.js` can look it up too - `myhome-light.js`/`myhome-shutter.js`/`myhome-energy.js`/`myhome-thermo-zone.js` all `require('./resources/myhome-common-utils')` (the same isomorphic module their `.html` already uses) to call `findRegisteredPoint`/`buildAPL_Dotted` when building `msg.mh_nodeConfigInfo`'s `.room`/`.description`/`.pointid_UI`.

- **Architecture: static HTML per section + lazy `editableList` only.** Each category's header, search box, and `<ol>` are plain hand-authored HTML in the template (mirroring the still-static Advanced section), *not* generated by JS. Only what varies in behavior lives in `POINT_CATEGORY_CONFIGS` (`{key, defaultIcon, hasGroup, plainId, addressPlaceholder, busLevelOptions}` - see the dedicated bullets below for `plainId`/`busLevelOptions`). `setUpPointsList(config)` mounts the `editableList` widget on that existing markup, lazily - only the first time a section is expanded (`builtCategories[config.key]` guard; all categories also wait on one shared `spriteReadyDeferred` so whichever opens first doesn't race the icon sprite). This replaced an earlier version that generated the whole section DOM via JS (`buildCategorySectionDom`): that saved a few lines of per-category markup but cost more than it saved - jQuery-appended elements have no whitespace text nodes between them (silently ate the header's icon/label gap until patched with CSS), and any field built that way sits outside Node-RED's default-value population (see next bullet), needing manual initial-state wiring instead of getting it for free.
- **`oneditsave` must not read `.editableList('items')` from a category never opened this session** - it has no live rows; doing so would silently wipe its previously-saved points. Fix: check `builtCategories[config.key]`, and when false, copy that category's points through unchanged. Verified live, including with *both* sections left fully collapsed.
- **A field only picks up its saved value for free if it lives in the static template, not JS-built markup**: Node-RED's own default-field population (`preparePropertyEditor`) runs once, *before* `oneditprepare` - it can only find elements that already exist. Save's write-back (`editor-tab-properties`'s `apply()`) runs *after* `oneditprepare` though, so Save works correctly either way. This is why the Light-only "refresh loads on connect" checkbox (`lights_onconnect_refreshloads`) lives in the static template inside `#mh-gw-tab-light`, not JS-built.
- **Room suggestions are global**, shared across every category (`refreshAllRoomSelects()`, no `config` param - reverses an earlier per-category-scoped version, dropped once cross-category suggestions turned out to be wanted). An unbuilt category's rooms come from saved `points`; a built one's from its live rows (so an unsaved room is picked up immediately, including by other already-open categories - a side effect of going global, not separately implemented).
- **Section header counts are populated eagerly at `oneditprepare`**, straight from `scope.points` (not left blank until the `editableList` is built). `refreshPointsCount(config)` (live row count) takes over once a category is actually being edited.
- **New-point Room field defaults to the `<select>`, not the free-text input**, once at least one room already exists - picking an existing room is the common case. `refreshAllRoomSelects()` pre-selects the first room and fires `change` so `lastCommittedRoom`/summary stay in sync, only for a row with no room committed yet.
- **AP auto-discovery (Light + Shutter + Energy + ThermoZone) is passive**: `myhome-gateway.js`'s `parseFrame()` records the WHERE of every `OWN_LIGHTS`/`OWN_SHUTTERS` frame into `node.discoveredPoints.light`/`.shutter` (in-memory, never persisted), parsing WHERE with `/^\*<WHO>\*\d+\*(#?\d{1,4})(#4#(\d\d))?##/` (WHO=1 or 2) to split it into a clean `pointid`, `isgroup`, and `buslevel` (`''` for the private riser, a 2-digit string for a local bus) - keyed in the map by the full `pointid+busSuffix` string (`pointbusid`) so the same AP number on the private riser and on a local bus are tracked as distinct devices. `GET /myhome-bticino/gateway/:id/discovered-points/:category` is a genuinely generic route (`gatewayNode.discoveredPoints[req.params.category]`) - a category not (yet) tracked just returns no points, not an error (no category is currently in that state, but the route stays generic for whatever comes next). No "refresh" button/command - purely passive.
- **Energy's auto-discovery (WHO=18) needs a different request-vs-response signal than Light/Shutter's**, because unlike WHO=1/2 (where a status frame has no `#` but a request does), a WHO=18 request AND its response both carry the `#` (`*#18*<where>*<dim>##` vs `*#18*<where>*<dim>*<val>##`, confirmed against the official protocol doc, `WHO_18.pdf` - Energy Management Functions) - so `parseFrame()`'s WHO=18 regex, `/^\*#18\*(5\d{1,3}|7\d{1,3}#0)\*[\d#]+\*(\d+\*)?\d+##/`, keys off a trailing value instead: the WHERE alternation (`5N` meter / `7N#0` actuator) already excludes `WHERE=1N` (Stop&Go, not a concept this node pack has), `[\d#]+` swallows the dimension token whatever its shape without needing to name it (`113`, `52#Y#M`, `511#M#D`, ...), and requiring at most one extra `<tag>*` segment before the final value both rejects a bare request (no value at all) and a multi-value dimension like actuator status (dim `71`, six values) that `myhome-energy.js` doesn't read anyway - deliberately scoped to only the dimension *shapes* `myhome-energy.js` currently handles (`51`/`52`/`53`/`54`/`113`/`511`/`513`), not to the full WHO=18 spec (Stop&Go, actuator enable/disable, totalizer reset, differential current level, ...). `buslevel` in the resulting discovered-point entry holds `'meter'`/`'actuator'` (from whether WHERE ends in `#0`), matching how the registry itself repurposes that field for Energy (see below).
- **ThermoZone's auto-discovery (WHO=4) is a `ZONE_DISCOVERY_REGEXES` array, not a single regex**, unlike WHO=1/2/18 - `myhome-thermo-zone.js`'s own `processReceivedBUSFrames` already has 5 separate checks (each keyed off one fixed, already-configured `config.zoneid`) for the 5 frame shapes it actually reads: master-probe temperature/set-point (dim `0`/`14`), zone operation type (`*4*<what>*<zone>##`, no dim token at all), actuator status (dim `20`, WHERE=`<zone>#<actuatorDigit>`), local offset (dim `13`), and zone operation mode via Central Unit (`*4*<what>*#<zone>##`). `parseFrame()`'s discovery mirrors those same 5 regexes 1:1 (same doc-section references in its own comments), just with the zone number as a capture group instead of a fixed literal, tried in order until one matches. All 5 capture the zone as `([1-9]\d?)`, not `(\d{1,2})` - WHERE `0`/`#0` means "all probes"/"Central Unit" itself, not a zone, and `\d{1,2}` would wrongly capture that as a fake "zone 0" (caught live against the real `*4*303*#0##` "set central unit off" frame from the protocol doc before shipping this). Deliberately scoped to only those 5 shapes - fan coil speed (dim `11`), complete probe status (dim `12`), valves (dim `19`), split control (dim `22`), holiday/scenario/weekly-program commands, and WHO=1004 (a separate top-level WHO for diagnostics) are all out of scope, matching what the node itself never reads.
- Both the gateway's own list and each device node's AP picker (`myhome-light`) independently call `discovered-points` and merge with `RED.nodes.node(gatewayId).points`, so a freshly-discovered AP doesn't stay invisible until the gateway dialog is opened+updated. AP found only via discovery are shown under a "not yet registered" pseudo-room.
- Sections use plain DOM show/hide, not `RED.tabs.create` (see widget reference below) - always collapsed on open regardless of prior state.
- **The AP browse popover + recap box are one shared function**, `setupApPointPicker(scope, config)` in `resources/myhome-common-utils.js`, called once from a device node's own `oneditprepare` with `{category, addressField, i18nPrefix, defaultIcon}` (plus, when needed, `plainId`/`buslevelField` - see below) - `myhome-light.html` calls it with `{category:'light', addressField:'lightid', i18nPrefix:'mh-light', defaultIcon:'mdi-lightbulb-outline'}`, `myhome-shutter.html` with `{category:'shutter', addressField:'shutterid', i18nPrefix:'mh-shutter', defaultIcon:'mdi-window-shutter'}`, `myhome-energy.html` with `{category:'energy', addressField:'meterid', buslevelField:'metertype', i18nPrefix:'mh-energy', defaultIcon:'mdi-flash', plainId:true}`, `myhome-thermo-zone.html` with `{category:'thermozone', addressField:'zoneid', i18nPrefix:'mh-thzone', defaultIcon:'mdi-thermometer', plainId:true}`. Every DOM id it touches is derived from `addressField` (`'node-input-' + addressField + '-browse-btn'`, `-browse-panel`, `-browse-search`, `-browse-tree`, `-recap-icon`, `-recap-text`, ...) except `#node-input-<buslevelField||'buslevel'>`/`-isgroup`/`-gateway`, which are literal (or, for `buslevel`, configurable via `buslevelField` - see the Energy/`metertype` repurposing note below). Neither `-isgroup` nor the bus-level field needs to actually exist in a given device's template - every read/write in this function is a plain jQuery call on an id selector, which no-ops safely on an empty selection (`findRegisteredPoint` then normalizes the resulting `undefined` to `false`/`'private_riser'` on its own) - `myhome-energy.html` and `myhome-thermo-zone.html` both have no `#node-input-isgroup` at all, and `myhome-thermo-zone.html` has no bus-level field either. **One exception, found live**: the browse-popover's own positioning code calls `.get(0).getBoundingClientRect()` on the bus-level element to size/place itself, and `.get(0)` on an empty selection returns `undefined` - unlike every other read/write here, that one throws instead of gracefully no-oping, so it needs an explicit fallback to the address field's own position when there's no bus-level element (exactly `myhome-thermo-zone.html`'s case) rather than relying on jQuery's usual leniency. A node wanting this feature needs only: the `<script src>` for `myhome-common-utils.js`, an id-substituted copy of `myhome-light.html`'s address-row/browse-panel/recap-box markup **including the `<hr>`-style divider right after the recap box** (easy to forget since it's a separate, easy-to-miss element, not part of the recap box's own `<div>` - already forgotten once when first extending to `myhome-shutter.html`), and the one `setupApPointPicker(...)` call - see that file's own function-header comment for the exact config shape. Extending to `myhome-shutter.html` also required restructuring its address row to match light's one-line layout (buslevel+address+group+browse button) - it previously put the group checkbox on its own second line, with no room reserved for a browse button; and shortening its `shutter-isgroup` label wording (was "This is a group reference", now "is a group" matching light's own) - the longer wording wrapped onto a second line and visually collided with the new browse button, only caught by rendering it live, not by inspecting the markup. **When a device's address row has nothing else competing for space** (Energy's ID field once its metertype+ID+browse layout was fixed, ThermoZone's zone-ID field from the start), let that field stretch to fill the row (`position:absolute; left:X; right:44px` - the 44px clears a ~34px browse button plus the project's standard 10px gap) rather than a fixed narrow width - a fixed width there was an actual regression caught live on Energy (large dead gap before the browse button) and fixed by switching to this anchoring; ThermoZone's row was built with it from the start instead of repeating the mistake.
  - **`plainId: true`** (Energy, ThermoZone) marks a category whose address is a flat ID with no `A.PL` structure - threaded into every internal `buildAPL_Dotted`/`buildAPL_FullDescrUI` call as the `forceRaw` argument (see `buildAPL_FullDescrUI`'s own header comment). Omit for an `A.PL`-addressed category (light/shutter); default is falsy, so their calls are unaffected.
  - **`buslevelField`** lets a category with no bus-level concept of its own repurpose that slot for a different per-point identity dimension instead, by pointing this at that field's id suffix - Energy's `'metertype'` (meter/actuator) is the only current example; default is `'buslevel'`.
  - The popover is a `RED.treeList` (see widget reference for its own gotchas), body-appended and `position:fixed` like the icon-picker below, spanning only from the bus-level dropdown's left edge to the browse button's right edge (not the full row, which would run under the field's own label). Rooms are one collapsed-by-default section each, no room icon, labelled with their point count (`'Salon (3)'`); each point's row is built via `buildAPL_FullDescrUI`/`iconSvgHtml`, with an empty room since the room is already the section header. A `SearchBox` filters via `treeList`'s own recursive filter (a room with no matching point stays hidden; one with a match auto-expands).
  - Picking a point must apply its `buslevel` too, not just address/group - the same AP number can exist on both the private riser and a local bus, so address+group alone don't identify it; the "not yet registered" pseudo-points synthesized from `discovered-points` need `buslevel` carried through for the same reason, and the dedup key comparing them against already-registered points needs `buslevel` in it too (mirroring the identical, already-correct key in `myhome-gateway.html`'s own auto-discovery merge).
  - The recap box shows the icon/room/description/AP/group of whatever registered point the current buslevel+address+group resolves to (via `findRegisteredPoint`, falling back to a "not registered" note), refreshing on any change to those fields or the gateway - including the change events the picker's own point-selection already fires.
  - The `<ol>` treeList builds (top-level list AND each room's own child list) carries the browser's own default 40px `padding-left`, uncleared by Node-RED's core CSS - `setupApPointPicker` clears it with one page-wide, once-only injected rule (`[id$="-browse-panel"] .red-ui-treeList-list {padding-left: 0;}`), rather than a rule scoped per node type, so a future node reusing this function needs no CSS work of its own.
  - A synthesized "not yet registered" point's placeholder description reads `common.points-unnamed-description` - **not** `mh-gateway.config.points-undefined` (an earlier, broken version of this code read that key from a device node's own `scope`, which auto-prefixes with the *calling* module's namespace per the i18n rule above, so it silently looked for a non-existent key in the device node's own locale file instead of gateway's). `points-unnamed-description` therefore lives in the shared `"common"` block (propagated to all 27 locale files) rather than gateway's own file - deliberately a different key name than `mh-gateway.config.points-description-placeholder-<category>` (an unrelated, pre-existing key: an input-field placeholder hint, not a display fallback - itself suffixed per category, e.g. `-light`/`-shutter`, after an earlier version hardcoded one shared key that kept showing a light-flavored example ("e.g. Ceiling light") even in the Shutters section).
  - **The recap box's icon+text markup must have zero whitespace between the two `<span>` tags** (`...</span><span ...>`, all one line, not one per span) - this is hand-authored static HTML, unlike the gateway's own equivalent row summary (`.mh-point-summary-icon`/`-text`, jQuery-`.appendTo()`-built, no whitespace text nodes possible) - a newline+indentation between the tags collapses to a visible extra gap on top of the intended `margin-left:6px`, which isn't obvious from reading the CSS alone and was only caught by measuring the live rendered gap against the gateway's own list.
- `.js` runtime file edits need an actual Node-RED restart (unlike `.html`, reloaded per page load) - Deploy only pushes flow/config, not node module code.
- Node-RED 5.0's dark theme (mid-2026) will clash with the Advanced section's hardcoded light colors (`#EFEFEF`/`#CCCCCC`) - pre-existing, cosmetic, worth revisiting via CSS variables next time that panel is touched.
- **Icons**: a curated MDI (Pictogrammers, Apache-2.0) subset as an SVG sprite ([resources/mdi-icons-sprite.svg](resources/mdi-icons-sprite.svg), 254 icons/~97KB), rendered as `<svg><use href="#mdi-xxx">` built via raw HTML strings (never jQuery's `$('<svg/>')` factory - wrong namespace). Everything icon-related waits on the sprite fetch resolving (`spriteReadyDeferred`) before building rows/picker - a `<use>` created before its `<symbol>` exists doesn't reliably re-resolve later. The fetch needs `$.ajax({dataType:'text'})`, not `$.get()` - jQuery auto-detects `image/svg+xml` as XML and silently parses it into a Document instead of a string.
- **Icon curation**: sourced via `npm install @mdi/svg` and reading `meta.json`/`svg/*.svg` directly - never hand-transcribed (a typo'd slug fails silently, blank icon, no error). Mostly MDI's own "Home Automation" tag (655 icons), narrowed down then extended back up over successive curation passes (303 icons as of this writing) by dropping overly granular variant families (dimmer percentages, per-country socket shapes, ...) while adding requested ones back in, grouped into 10 home-grown themes (not an MDI concept). Aliases/tags carried verbatim into `MDI_ICON_CATEGORIES` for search (British English vocabulary, hence the "UK terms only" placeholder). Regenerating/extending this set should reuse the same `@mdi/svg` approach - install the package (even just in a scratch dir), cross-check every candidate slug against its `meta.json` (typos fail silently) AND against the catalog's own existing slugs (skip ones already present instead of duplicating), and pull the real `<path>`/`viewBox` from `svg/<slug>.svg` into `mdi-icons-sprite.svg` - never write path data by hand.
- **Icon category order is display order**: `MDI_ICON_CATEGORIES.forEach(...)` (in `myhome-gateway.html`'s icon-picker builder) renders one picker section per array entry, top to bottom, in array order - reordering the top-level array is the only thing needed to reorder the picker. `lighting` and `openings` are deliberately the first two entries (this node pack's two most common device families), the rest keep their original relative order. All "lamp"-themed icons live in `lighting` and all shutter/window/door-opening icons in `openings` only - a new icon that's arguably both (e.g. a lamp shaped like something else) goes to `lighting` since that grouping is the more specific/deliberate one.
- **[resources/myhome-common-utils.js](resources/myhome-common-utils.js)** is an isomorphic module (works both `require()`'d server-side and `<script src>`'d client-side, via `if (typeof module !== 'undefined')`) - the shared home for logic every device config node's editor is meant to reuse, not just `myhome-gateway.html`. Exports: `buildAPL_Dotted(pointid, isGroup)` (raw code → `'A.PL'` notation, `'?.?'` for empty - a group has no A/PL structure at all, just a plain 1-99 group number, so `isGroup` skips the split entirely and returns the raw number as-is, `'?'` if empty); `buildAPL_FullDescrUI(description, room, apl, isGroup, translator)` (full `'<room> : <description> (<A.PL>)'` display text for a regular point, or `'(<prefix> <n>)'` - e.g. `'(Gr. 50)'` - for a group, no `A.PL` split since a group is just a plain 1-99 number; `translator` is optional/duck-typed, resolves the group prefix via `common.points-group-prefix`, falls back to the literal abbreviation `'Gr.'` without one); `findRegisteredPoint(points, category, buslevel, pointid, isgroup)` (resolves a device node's own buslevel/address/group fields to its matching entry in a gateway's `points` registry); `iconSvgHtml(iconId, size, defaultIcon)` and `ensureMdiSpriteLoaded()` (icon rendering + one-time sprite fetch, factored out of `myhome-gateway.html` so other nodes render identical icons without their own copy); `setupApPointPicker(scope, config)` (the AP browse popover + recap box, see above - the only one of these six a device node's own `.html` needs to call directly, since it drives the other five internally). All but `setupApPointPicker`/`ensureMdiSpriteLoaded` (browser/jQuery-only) work server-side too.
- Each category's list is sorted once, when first built, by `.localeCompare()` on the generated `buildAPL_FullDescrUI` display strings - deliberately simple, not re-applied on edit (would make a row jump around mid-edit).
- **The icon catalog (`MDI_ICON_CATEGORIES`)** lives in its own file, [resources/mdi-icons-definitions.js](resources/mdi-icons-definitions.js) (pure data, no gateway-specific logic), loaded via a plain `<script src>` before the node's own script block - runs once per editor page load, no "already loaded" guard needed. Named generically since a future device node's icon picker could reuse it (only its `labelKey`s currently point at `myhome-gateway`'s own locale namespace).
- **Eslint needs a `resources/**/*.js` config block** (browser globals, not Node's) - see `eslint.config.js`. `MDI_ICON_CATEGORIES`'s declaration needs `/* exported MDI_ICON_CATEGORIES */` (eslint lints files in isolation) and the consumer needs `/* global MDI_ICON_CATEGORIES */`.
- `RED.editor.showIconPicker` (the FontAwesome picker on every node's "Appearance" tab) was considered and rejected: its icon source (`RED.nodes.getIconSets()`) groups by installed module name, the wrong shape for a curated MDI set with theme/alias search. Its search-box-atop-a-grid layout was still worth mirroring.
- The Room field is a real `<select>` (+ `+ New room...`), not a styled `<input list>` (inconsistent cross-browser). Picking `+ New room...` swaps the select for a same-sized text input in place (reads as "this field became editable", not "a second field appeared").
- An expanded row's summary gets bold text + the **whole `<li>`** (not just `container`, which is inset from the `<li>`'s real edges and doesn't cover the remove button) gets a light grey background - the remove button needs its own `background:transparent` override too (core `.red-ui-button` styling gives it an opaque white background otherwise).
- Description/Room/Address fields all share the same left edge via `position:relative`/`position:absolute` zones with plain inline styles (not fixed pixel widths, not dedicated CSS classes) - matching the convention already used in `myhome-light.html`.
- Each category's search box is moved (in JS, after `editableList` initializes) into being the first child of `editableList`'s own bordered container, so search + list read as one panel - scoped to `.mh-gw-points-search-box` (never target `.red-ui-searchBox-container` bare, used all over Node-RED's own editor).
- The row summary shows the "A.PL" notation (converted for display only) - underlying storage keeps the raw code.
- **Bus level**: each point also carries a `buslevel` (`'private_riser'` or a 2-digit `'01'`-`'15'` local bus), a `<select>` placed immediately before the Address field on the same row - same 16 options/labels (`common.riser-private`/`common.riser-localbus-01..15`) as `myhome-light.html`'s own `buslevel` field, reusing the already-shared `"common"` locale keys. Defaults to `'private_riser'` when unset (points saved before this field existed). The auto-discovery dedup key (comparing already-registered points against newly-discovered AP) has to include `buslevel` too - the same AP number on the private riser and on a local bus are two distinct devices, not a duplicate.
- **A category with nothing meaningful to put in the bus-level slot doesn't get a new flag - it gets a one-entry `busLevelOptions`.** `thermozone`'s category config sets `busLevelOptions: [{value:'private_riser', i18nKey:'common.riser-private'}]` (a real option list, same shape Energy already uses for its 2-option meter/actuator repurposing - just narrowed to one entry) rather than a dedicated `hasLocalBus:false`-style boolean. The row-builder (`addItem`) then applies one small, category-agnostic rule after building whichever option set applies: `if (busLevelSelect.find('option').length === 1) { busLevelSelect.prop('disabled', true).css('color', 'LightGrey'); }` - a select with one option has nothing to actually pick anyway, so this only affects how it *reads* (fixed vs. interactive-but-single-choice), and it applies automatically to any future single-choice category with zero extra config surface. This was an explicit correction: an earlier draft of this design added a new `hasLocalBus: false` flag for exactly this case before the user asked for it to reuse `busLevelOptions` instead, precisely to avoid the config schema accumulating one new orthogonal flag per future category.
- A row added via "Add a point" auto-expands immediately (a blank row otherwise shows a garbled "undefined" summary) - gated on `isNewBlankRow = !data.point`, the only case where `addItem` gets no real `point`.
- **Icon-picker popover**: appended to `document.body`, `position:fixed`, positioned via `getBoundingClientRect()` (not jQuery's `.position()`) - replaced an earlier version left as a row sibling (`position:absolute`), which worked for width-matching but got clipped by a small category's own scrollable list (e.g. a fresh 1-row Shutter section left almost no room for the picker). Width matches the Description/Room row's right edge; `max-height` is `window.innerHeight - top - 10`, using whatever viewport space remains rather than a fixed value.
- **Being body-appended also escapes Node-RED's `.red-ui-editor-dialog`-scoped CSS** (dialog typography, form-control chrome) - `#mh-gw-icon-picker-popover` (and, for the same reason, every device node's own `-browse-panel`: `myhome-light.html`/`myhome-shutter.html`/`myhome-energy.html`) repeats `font-family`/`-size`/`color` explicitly rather than relying on inheriting the dialog's own styling. Plain text picks this up via inheritance; `<input>`/`<button>` do NOT inherit `font-family` from an ancestor the way text does (their browser default wins) - needs an explicit `font-family:inherit` etc. on the popover's own form controls too.
  - **These 4 occurrences were originally `font-family:var(--red-ui-primary-font); font-size:var(--red-ui-primary-font-size); color:var(--red-ui-primary-text-color)` (mirroring Node-RED's own `.red-ui-menu-dropdown-portaled` convention, on the theory those custom properties are defined once on `:root` and readable from anywhere) - now hardcoded (`-apple-system,BlinkMacSystemFont,'Segoe UI',Roboto,Helvetica,Arial,sans-serif` / `14px` / `#202020`) instead, confirmed live on a real deployment: on Node-RED 4 that variable resolves to a visibly lighter grey than on 5 (icons and text in these popovers rendered washed-out on 4, correctly dark on 5 - not a dark-theme issue, both were light theme). A `var(--red-ui-primary-text-color, <fallback>)` wouldn't reliably fix this - the fallback in `var()` only applies when the custom property is *undefined*, and the more likely explanation here is that Node-RED 4 defines it, just with a different (lighter) value than 5 does. Hardcoding a value matching what 5 already renders was the only fix guaranteed correct on both versions without first confirming which case it actually is.
- **Known, accepted limitation: the popover doesn't track its button if the list behind it scrolls** (position computed once, at open time). A "close on any scroll" fix was tried and reverted - it also closed the picker when scrolling its own icon grid, since a bare capture-phase `scroll` listener on `document` can't distinguish "the list behind it scrolled" from "the grid inside it scrolled". A `iconPicker[0].contains(e.target)` check would fix that, but wasn't pursued - the user judged the floating behavior an acceptable trade against further side-effect risk. Revisit only if asked.
- `editableList`'s native remove button is positioned `top:50%` of the whole `<li>`, so it drifts mid-row once expanded - normal/expected for a variable-height row, deliberately left alone.
- **CSS injected via `$("style").append(...)` needs both injection timing and specific-enough selectors to beat Node-RED's core CSS, with no `!important`**: (1) inject inside `oneditprepare` (loads after core CSS, wins specificity ties by source order) rather than a static `<style>` block; (2) scope any bare `<select>`/`<input>`/`<button>` override with a stable id ancestor (e.g. `#node-config-input-points-shutter .mh-room-select`) - a bare class selector has *lower* specificity than core's class+type rules and loses even when injected last (found the hard way, twice - once for `.mh-room-select`, once for the search box's height). If a class-scoped override doesn't visually take effect, don't reach for `!important` - enumerate the actually-matching rules live (`el.matches(rule.selectorText)` over `document.styleSheets`) and prefer an id selector on the target element itself. (3) Guard the injection itself with a one-time check (`if ($('#my-injected-styles').length === 0) {...}`) - `oneditprepare` re-runs on every dialog open, so an unguarded append re-adds the same CSS text each time (harmless but unbounded DOM/memory growth) - apply this guard to any future `$("style").append(...)` block in this project, including `myhome-scenario.html`'s own (currently unguarded) rule-row styles if that file is touched again.

### Local UI verification workflow (Playwright)

A local, disposable Node-RED instance driven by Playwright ([playwright-core](https://www.npmjs.com/package/playwright-core) + the system's Edge via `channel: 'msedge'`, no browser download needed) beats screenshots + a manually-restarted docker for checking CSS/layout fixes - caught real bugs screenshots alone hadn't:
- Install `node-red` + this repo as a `file:` dependency in a scratch dir (`npm install node-red "file:<repo path>"`) - npm symlinks it, so edits are picked up immediately, no republish step.
- Seed a flow via the **Admin HTTP API** (`POST /flows`), not by hand-editing `.node-red/flows.json` - a config node with no `z` at boot gets miscategorized into "Recovered Nodes", which deploying via `POST /flows` right after startup avoids. Keep the seed JSON outside `.node-red/` (overwritten on every deploy).
- Dismiss the one-time "Enable Update Notifications" dialog and (5.0) the "Welcome to Node-RED 5.0!" tour overlay (button click + `Escape`) before interacting with anything else.
- **A `.html` edit needs a full Node-RED restart, not just a page reload** - even via a live symlink, Node-RED serves/caches the combined editor-side HTML server-side.
- To reach a node's edit dialog: `dblclick` the node **with `{force:true}`** (an SVG `<rect>` sibling otherwise intercepts the click), then click the pencil icon next to a config-node field - avoids the "Global Configuration Nodes" sidebar tree, which shows the config node as empty for the same z-scoping reason.
- `page.evaluate(() => el.getBoundingClientRect())`/`getComputedStyle()` on live elements is far more conclusive than eyeballing a screenshot for alignment/sizing questions - caught two real regressions a screenshot made look "close enough" (see the CSS-specificity bullet above).
- **`SearchBox` listens on native `keyup`, not `input`** - Playwright's `page.fill()` only fires `input`/`change`, so it silently never triggers the widget's debounced filtering. Simulate real keystrokes instead: `locator.pressSequentially(text, {delay: 30})`.

### Buttons next to an input

A button next to a text input needs a **deliberate gap** - not the button's own width mistaken for one (leaves zero visible margin), and not a fixed width narrower than its natural size either (squashes the button's content instead of creating a gap). Convention that works: give the button its natural size, then add an *explicit* margin/reserved space on top of that (for absolutely-positioned pairs, the input's reserved offset must exceed the button's rendered width, not just match it).

**The gap is Node-RED's own native standard: exactly 10px.** Confirmed by measuring its built-in config-node picker (every `.red-ui-button` in it carries `margin-left: 10px` in Node-RED's core CSS). Use 10px as the literal target for any button-next-to-input spacing in this project, not an approximation.

## Node-RED editor widget reference

Before reaching for a `RED.*` editor UI widget, check this table rather than re-litigating it each time. Built by inspecting Node-RED **5.0.0**'s own source and cross-checking usage in its bundled core nodes (switch, change, function, http request, mqtt, link, catch, global-config) - a widget used by a core node is a strong stability signal (Node-RED can't break it without breaking those).

**Officially documented**: `TypedInput`, `EditableList`, `SearchBox`, `TreeList`.

- **`SearchBox`'s `change` callback MUST be passed as a widget option, never chained via `.on('change', ...)`** - it's a jQuery-UI-style widget whose internal `_trigger('change')` fires a DOM event literally named `searchboxchange`, not `change` (confirmed from the widget factory's `_trigger` source), so a plain `.on('change', fn)` binding never runs, silently. Pass `change` as a constructor option instead (matches Node-RED's own core palette search). Any `.searchBox(...).on('change', ...)` in this codebase is suspect.

**Undocumented, but used by Node-RED's own core nodes in 5.0.0** (safe to reuse): `RED.tabs.create` (`mqtt-broker`, `function`), `RED.popover` (`function`).

**Present in the source but not found in core-node use**: `autoComplete.js`, `checkboxSet.js`, `menu.js`, `panels.js`, `stack.js`, `toggleButton.js` - test live before relying on them.

**`treeList`/`RED.tabs.create` are NOT broken on v5** - confirmed by their use in core `mqtt-broker`/`function`/`link`/`catch`. What actually went wrong in this project: `treeList` was called with `data` in the constructor (`.treeList({data: ...})`), which silently renders nothing - core usage always initializes without data, then calls `.treeList('data', theData)` separately (the fix `myhome-light.html`'s AP picker now uses). `RED.tabs.create` was structurally near-identical to `mqtt-broker`'s but rendered no tab strip live, root cause never found - `myhome-gateway.html` uses collapsible sections instead (simpler anyway, confirmed working). Takeaway: when a `RED.*` widget misbehaves, compare the exact call pattern against a core node's usage before concluding it's a platform bug.

- **`treeList`'s own `<ol>` carries the browser's default 40px `padding-left`** at every nesting level, uncleared by Node-RED's core CSS (which only resets `margin`/`list-style-type`) - left alone, a large blank strip before every row's own icon/chevron, compounding once per level of nesting. `setupApPointPicker` (see "Gateway BUS points registry" above) clears this with one page-wide rule targeting every node's panel at once, e.g. `[id$="-browse-panel"] .red-ui-treeList-list {padding-left: 0;}`, injected once regardless of how many node types use it.
- **An item's `icon` is read as a CSS class name (`<i class="...">`) only when it's a plain string** - anything else (a jQuery object, a DOM element) is appended as-is instead. Pass `$(iconSvgHtml(...))`, not the raw HTML string, to render a custom SVG icon rather than have it misread as a broken class name.
